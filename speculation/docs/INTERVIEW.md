# 面试讲述与追问

## 先讲具体问题

“我重写了跨请求草稿缓存的实现和 vLLM 接入。原版能在特定重复任务上加速，但缺少明确的提交边界和可靠反馈，而且本地有低质量草稿时会挡住共享命中。新版把检索、提交、调度验证和生命周期分开实现，再用原生推测、无门控、旧优先级和默认 runner 对照定位收益。”

随后只引用 RESULTS.md 中本版本的实际数据。旧版 6.30× 不是本版本的结果，不用于替代重跑。

## 一次请求怎么经过系统

1. 原生目标模型计算并采样，worker 的 token buffer 更新为已确认的输出。用真实 prompt 长度区分提示词与生成片段。
2. 用已确认序列的尾部 12/8 个 token 查询其他请求的完整 8-token 续写。默认长上下文共享候选优先，失败后保留原生 n-gram 结果。
3. 返回草稿给原生调度器。调度器可能截短或根本不安排该草稿，所以检索命中只算 proposal，不能算 verified。
4. 下步用实际调度的草稿和 sampled token 对齐。比如提出 8 个，只安排 4 个，输出为“接受 2 个 + 1 个目标 token”，则接受数是 2/4，不是 2/8，也不是 3/4。
5. 只把更新后的 committed buffer 发布至索引。被拒绝的草稿不会因为“曾被提出”而写入缓存。整批先读后写，避免同一步批内顺序影响来源。
6. finished 事件删除游标与 pending；生成片段继续作为缓存候选保留至 TTL/LRU 淘汰。暂未调度和预占不是结束，不能靠“这批没出现”清理。

## 为什么这算系统实现

可以现场打开 `core.py` 解释提交游标、候选条目、pending 三套状态分别负责什么，再打开 `runtime.py` 指出 actual scheduled 草稿如何与 worker req_id 对齐。补丁入口和源码散列能证明接入真实执行路径，原始 JSONL 能证明草稿被验证，而不仅是一个 Python 检索微基准。

同时应明确归属：模型 forward、Attention、KV Cache、拒绝采样与目标验证均复用 vLLM；没有开发 CUDA 算子。系统岗位的技术深度来自状态语义和端到端证据，不需要虚构算子重写。

## 为什么接受率高也可能不快

单步净收益近似要求：`检索维护成本 + 一次验证成本(k) < (1 + 期望接受数) × 普通 decode 单步成本`。验证多个 token 会改变 attention/矩阵形状；CPU 索引维护、批大小、编译/CUDA Graph 路径也会影响耗时。因此同时报告实际接受量、目标模型执行步数、CPU 耗时和无诊断端到端时间，不能直接用接受率推导加速倍数。

门控目前用接受 token 数作启发式，未按 GPU 实测成本校准；“两次平均少于 2，冷却 32 步”不能说成最优策略。候选按来源分别反馈，来源频繁更换会削弱门控积累，实测消融没有改善时就应承认。索引维护仍有成本，即使没有任何命中。

## 为什么不直接说 lossless

算法上草稿必须由目标分布验证；实际栈还会因 batch、验证长度、kernel 和浮点数值路径改变贪心分支。必须把普通性能和 batch-invariant 的完整输出测试分别报告，并保留原生 n-gram 对照。若共享组与原生组都偏离无推测输出，先调查共同数值路径；若只有共享组变化，进一步检查候选内容、截短、批次与原生无共享复现，不能直接下结论。

## 为什么要测默认 V2 runner

扩展接在支持的 V1 runner。0.32 默认可能走 V2，单改 V1 源码并不意味着特性生效。曾通过“追踪记录完全缺失”发现这个问题，随即把那批运行移入 development，并显式固定 runner；最终还要与默认 V2 原生模式做外部比较。只能把同 runner 组内改善归因于检索策略，跨 runner 的结果需要单列。

## 复杂度与边界

自己实现的每请求查询最多尝试两个固定长度键；每步维护最多 32 个完整窗口，每键最多两个来源，最多 50,000 个键。上限控制 CPU 工作和条目数量，但不等于精确字节预算；Python 对象和活跃请求游标另有开销。TTL 按 proposer 调用步计，不是秒。长历史超额窗口被主动跳过，会牺牲召回率。

仅用于单引擎单租户；不声称多租户隔离、跨进程缓存、在线延迟 SLO、普通对话收益或生产就绪。下一步优先依据真实轨迹和 CPU 分解决定是否做更紧凑的 C++/数组索引，而不是先承诺进一步加速。
