# 排错记录

## 原始仓库复核

原仓库 `68c45a1c9078c48012e7fd736a526e3161cf35e5` 的验证脚本可以复算旧实验：高重复整数续写 6.30×/4.26×，普通请求输出逐 token 5/8 一致。旧版报告已承认普通请求的数值问题；本次不删掉这个事实，也不把旧数据标成重写后的数据。

## 短匹配挡住共享候选

旧优先级只在本地 n-gram 无草稿时查共享缓存。独立代码审查提出一个可检验的问题：“有本地草稿”不能代替“草稿有效”，较短匹配可能挡住共享匹配。新版增加共享长上下文优先，并保留 `shared_first=false` 对照。早期开发运行缺少收益后来确认与 runner 绕过有关，不能拿它作为优先级问题的实验证据。最终应使用同版本、特性确实生效的优先级消融：单种子重复 batch 8 约 0.296→0.210 秒，但普通问答 batch 8 约 1.159→1.250 秒；这是局部取舍，不能称普遍改善。

## runner 选择绕过扩展点

第一次 0.32.0 集成运行表面成功，但预期 JSONL 文件完全没有生成。检查启动日志发现加载的是 `v1/worker/gpu/model_runner.py`，而审查和补丁的入口是 `v1/worker/gpu_model_runner.py`。本地环境默认启用了 V2 runner。

处理：中断仅本项目启动的实验进程，将该批移入 `results/development/inactive-runner/`，不用于最终特性证据；为所有主对照显式设置 `VLLM_USE_V2_MODEL_RUNNER=0`；诊断脚本现在强制检查 trace 和索引初始化记录；另加默认 V2 原生外部对照。固定后冒烟运行记录到共享草稿 56/56 token 接受，并在 finished 事件后 cursor/pending 归零。

## macOS 元数据

早期传输产生 AppleDouble `._*.py`，它们不是 Python 业务源码。新归档禁用 copyfile/xattr，远端清理这些文件，源码指纹枚举显式排除 `._*`。该问题不改变检索决策，但会污染可复算的源码证据，因此不能放任混入最终包。

后续严格一致性与性能结论以最终 RESULTS.md 为准，开发测量和追踪耗时不能挪用为无诊断加速数字。

## 外部和内部请求 ID 对齐

初次汇总发现全局接受统计非零、按工作负载的统计却为空。原始 JSONL 已保存，检查 0.32.0 的 `v1/engine/input_processor.py:371` 可见 worker ID 在 external ID 后追加 `-` 和 8 位随机十六进制串。结果分析器原先用外部 ID 直接匹配，遗漏了这些事件。

修复仅影响结果分析：先从真实 schedule 事件构建外部到内部的唯一映射，要求每个计时请求都能唯一找到 worker ID，缺失或歧义直接失败；增加两个回归测试。不会改动运行中的检索策略、请求负载或计时原始数据。最终在本地重新分析原始结果；阶段记录中保留测量时的分析器散列，分析修正另存审计，不能假称原来的聚合已经正确。
