# RecallSpec v2：重写内容、实测结果与边界

本轮完成跨请求草稿索引、显式 worker 接入、真实验证反馈与可复算对照。**收益集中在缓存预热后的可重复续写；不支持“一般问答普遍加速”或“普通 BF16 始终逐 token 一致”的结论。**

最适合写进简历的性能结果是：RTX 4090、Qwen2.5-3B BF16、128-token 固定高重复整数续写、batch 1、缓存预热后的三种子延迟中位数，由 **1.088s 降至 0.160s（6.78×）**；该条件下包含首轮的 12 个请求与无推测基线完整输出一致。这里的加速比只统计各进程后续三轮的中位数，不包含任务首轮、引擎初始化和模型加载。

## 实质实现

- 将旧版启动时隐式覆盖改为 vLLM 0.32.0 GPUModelRunnerV1 的显式、版本/源码散列锁定扩展点；保留原始 worker 恢复工具。
- 根据真实 prompt boundary 和 committed token buffer 维护生成续写游标，整批先查后写；按原生 finished 事件清理，区分批次缺席与请求结束。
- 实现 50,000 键上限、每键两个来源、精确 token 匹配、写入步 TTL、LRU 与每请求每调用最多 32 个新窗口的维护预算。
- 对齐实际 scheduled 草稿前缀与 sampled 结果；截短按实际长度统计，提出未验证和空输出不当成拒绝，未确认草稿不写入索引。
- 默认 12/8-token 共享匹配优先，回退原生短 n-gram；用真实接受数进行候选冷却与重新探测。门控为预设启发式，不能声称学得了净收益最优策略。

模型 forward、Attention/KV、原生 n-gram、调度验证与 rejection sampler 均复用 vLLM；没有重写 CUDA/Triton 算子。实现取舍见 [DESIGN.md](docs/DESIGN.md)。

## 测量协议

主对照采用同一个 V1 runner、单卡、同步调度、FLASH_ATTN、BF16、max_model_len=4096、max_num_seqs=8、gpu_memory_utilization=0.75、temperature=0、固定 128 输出 token，默认关闭 APC。原生无推测和原生 n-gram 计时组恢复原始 worker 和调度器；自定义组才启用 worker 补丁。所有组使用相同非实验任务预热，关闭 trace 写盘计时。

种子 71/72/73 用于四模式性能评估，模式顺序预定轮换；74 用于 64-token 严格测试，75 用于独立机制诊断，77 用于 128-token 严格测试；7B 单列种子 76。门控阈值在评估前固定，没有依据评估结果挑选最佳配置。三个种子不足以宣称统计显著性。

工作负载是可重放的合成 prompt，经模型 chat template 渲染：repeat 为整数序列；general 为 12 个技术主题轮换并改变 case ID；conflict 为相同尾部指令、前部不同倍数参数。后两者也可能复用内容，不是真实业务流量，也不是完全无复用负对照。每种负载先 batch 1 后 batch 8；batch 8 继承 batch 1 缓存。所谓“首轮”是该任务组首轮，不是空索引或冷引擎。

## 3B 主性能：后续轮延迟

表内为每种子后续三轮调用的中位数，再跨三种子取中位数；单位秒。ratio 为无推测 / 共享有门控。离线批量 generate 延迟不是在线 TTFT/TPOT 或到达率驱动的吞吐。

|---|---:|---:|---:|---:|---:|---:|---:|
| 重复续写 | 1 | 1.088298 | 1.234533 | 0.160583 | 0.160450 | 6.783× | 12/12 |
| 重复续写 | 8 | 1.266996 | 1.356239 | 0.209784 | 0.210637 | 6.015× | 90/96 |

普通技术主题 batch 1 的共享组延迟约增加 **13.7%**，原生 n-gram 也有额外验证开销。batch 8 技术主题只有约 2.5% 的中位数差异，不解释为一般问答收益。门控与无门控几乎相同，**本轮没有证明新增门控带来稳定净性能提升**。

### 首轮与慢批不能隐去

3B 重复任务 batch 1 首轮的三种子中位数为无推测 1.106s、共享 1.265s；同一进程四次调用的耗时总和分别为 4.372s、1.746s，合计口径约 **2.50×**，小于只看后续轮的 6.78×。

重复任务 batch 8 的四次调用总耗时中位数为 5.063s、1.925s，合计口径约 **2.63×**；个别调用会回到约 1.3s，后续轮中位数 0.211s 不能代表尾部。普通模式 batch 8 完整输出仅 90/96 一致，其中首次分歧为位置 1 的逗号/空格；原生 n-gram 也出现部分同类差异。因此不把 6.02× 写成无条件、严格等输出的批量加速成果。所有首轮和慢批均保留。

## 正确性、状态与容量

| 验证 | 条件 | 结果 |
|---|---|---|
| 纯策略、worker 适配及分析回归 | 无模型 + fake worker 状态 | 31 项通过 |
| 完整 token 对照 | 3B，batch-invariant，64 输出 token，种子 74 | 共享/无推测、共享/原生、原生/无推测分别 81/81 |
| 完整 token 对照 | 3B，batch-invariant，128 输出 token，种子 77 | 共享/无推测、共享/原生、原生/无推测分别 81/81 |
| 容量压力 | CPU-only，1000 请求，64000 次插入 | 键数 50000，淘汰 14000，live cursor/pending 为 0 |

CPU 容量探针在 macOS/Python 3.9.6 上测试纯 Python 核心，当前分配约 29.5MB；每键只有一个来源，不是最大双来源内存，也不是 GPU 性能数字。实际引擎与回归另在 Linux/Python 3.12.3 上验证。31 项测试覆盖真实提示词边界、未完整生成续写、来源排除、TTL、淘汰、截短反馈、未调度/空输出、批内先读后写、native 优先级消融、finished 清理以及外部/内部 ID 映射。

普通 BF16 的 324 个主性能请求中，共享与无推测为 **241/324** 一致，原生 n-gram 与无推测为 **240/324**。不能把严格模式通过外推到普通路径；也不能仅凭共同出现差异就认定全部原因相同。未使用 logprobs=0 作为“修复”。

## 机制诊断：实际送去验证的草稿

以下来自独立种子 75、开启追踪的运行，统计包含任务首轮，不包含无关预热。计数按原始 schedule 事件把 worker 内部 ID 与外部请求逐一对应。追踪耗时不用于主加速数字。

| 负载 | batch | 原生 n-gram 目标执行步 | 共享目标执行步 | 共享接受 / 实际验证 token |
|---|---:|---:|---:|---:|
| 重复续写 | 1 | 375 | 157 | 224 / 224 |
| 重复续写 | 8 | 378 | 160 | 2464 / 2512 |
| 技术主题轮换 | 1 | 362 | 362 | 0 / 0 |
| 技术主题轮换 | 8 | 384 | 368 | 762 / 960 |
| 冲突指令/重复参数 | 1 | 329 | 326 | 6 / 40 |
| 冲突指令/重复参数 | 8 | 335 | 234 | 2026 / 2280 |

重复任务共享草稿接受率 batch 1 为 224/224，batch 8 为 2464/2512（98.1%），不是所有负载 100%。整体共享验证 6016 token、接受 5482；候选冷却触发 10 次。该轨迹最多 7137 个键，不能替代 50000 键的独立容量压力检查。

反馈步条件下，共享逻辑增量 Python CPU 时间中位数为重复 batch 1 约 0.043ms、batch 8 约 0.065ms；仅包含有验证反馈的 proposer 调用，不是所有调用平均，也不是 GPU kernel 时间。统计不包含 trace 文件写入，不能与端到端时间直接相减求净收益。

## 优先级、APC、默认 runner 与 7B

旧优先级消融只在本地 n-gram 无草稿时查共享索引。单种子 71 下重复 batch 8 从 0.296s 降至共享优先的 0.210s；但技术主题 batch 8 从 1.159s 增至 1.250s。batch 1 重复任务几乎相同。它支持局部取舍，不支持共享优先在所有场景最优。

APC 开启后单种子重复任务 batch 1 为无推测 1.093s / 共享 0.162s，batch 8 为 1.253s / 0.749s；共享组也有慢批，batch 8 输出 23/24 一致。不能从此声称与 Prefix Cache 稳定叠加。

默认 V2 runner 的原始源码外部对照（单种子 71），重复任务 batch 1 无推测/原生 n-gram 为 1.314/1.445s，batch 8 为 1.521/1.606s。它证明本轮另测了默认路径，但主三种子策略比值仍限定在同一个 V1 runner，不能跨 runner 混合归因。

7B 单种子 76：重复任务 batch 1 为 2.122→0.284s（7.48×），batch 8 为 2.242→0.388s（5.78×）；重复任务 27/27 输出一致。包括技术主题后仅 33/54 一致。7B 数据是单次跨模型可行性检查，不是普适性或生产部署证明。

## 证据、源码与可复算性

最终阶段、请求总数、所有运行时源码散列、真实长度、trace 容量与排空检查见 [release-verification.json](results/final/release-verification.json)。严格测试每个请求都保存完整输出 ID；普通性能数据也不删除不一致或慢批。

测量时冻结了检索实现、worker 补丁和负载脚本。分析器后来修正了 external ID 与追加随机后缀的 worker ID 映射，增加两个回归测试；修正不改原始输出或耗时，测量时与修正后的分析器散列同时保留。开发中默认 V2 绕过 V1 调用点的无效特性运行已移入 development/inactive-runner，不能算最终实现验证。详见 [DEBUG_LOG.md](docs/DEBUG_LOG.md)。

## 简历与后续边界

可强调显式引擎接入、提交与验证状态分离、真实调度反馈、有界维护和适用场景下的复用加速。建议只用条件明确且逐 token 对齐的 3B batch 1 热缓存 6.78×，并说明普通问答开销及数值差异；不写一般对话加速、普遍 lossless、多租户生产可用或算子重写。

下一步若继续优化，应基于真实轨迹检查负收益时完全跳过推测、候选选择与尾延迟，而不是将更多启发式开关当作收益。当前公开 GitHub 仓库未推送，不能用旧版本链接代替本地新版证据。
